# LCC plan, Q4 2026

Status: **approved 2026-10-20** (decisions in §7). Nothing is filed or posted yet.
Written 2026-10-20 against `main` at `54cf875` (v1.2.0, after PR #65 and #76–#82).

Rules this plan keeps: local and offline by default, no telemetry without explicit opt-in,
user text is never rewritten (every cut is byte-identical or recallable with a receipt), and
every number below is either a measurement run for this plan (section 1–2, reproducible with
the commands given) or cited from a file in this repository. Anything else is labelled
**hypothesis**.

**Limits of the evidence in this plan.** One machine (macOS arm64, Python 3.14.3, 10 CPUs),
one run per measurement, five sessions from one maintainer. The input map (section 2) uses a
scratch analysis script, not product code, and an approximation explained there.

## 0. One-sentence thesis

> lcc removes what a coding agent no longer needs from its context, keeps every byte it
> removes one `recall` away, and proves both with a receipt.

### Glossary

| term | meaning |
| --- | --- |
| **context** | everything sent to the model on one request: system prompt, tool schemas, injected instructions, the transcript |
| **`lossless`** | a removed tool output is replaced by a pointer to an identical output that is still in context. Nothing leaves the context. |
| **`recoverable`** | `lossless`, plus old file reads replaced by a "re-read" pointer when the file is unchanged (on disk with `workspace_root`, otherwise by transcript proxy) |
| **`stashed`** | an old tool output is moved to the local stash and replaced by `[removed: N tokens · lcc recall <id>]`; `recall` returns it byte for byte after re-checking its hash |
| **stash** | the local, content-addressed store of removed outputs (`~/.cache/lcc/stash`, `0700`/`0600`, `LCC_STASH_DIR`) |
| **`recall`** | CLI command and MCP tool that returns a stashed output by id |
| **receipt** | the report a pass emits: what was removed, why, by which rule, token counts, hashes, cache effect. Today: the JSON report and `cache_effect`; the user-facing form is item C2 below |
| **`lossy`** | experimental, failed two blind audits ([REAL_SESSION_BENCHMARKS.md §2](../REAL_SESSION_BENCHMARKS.md)); not part of the product story |
| **MSI** | Minimum Sufficient Inference, a research protocol (context IR, planner, verifier, inference receipt). Frozen as a research release by [ADR 0022](../adr/0022-research-release-freeze.md). Not the product. |

### Product vs research

| product (supported, measured on real sessions) | research (frozen or experimental, no product claims) |
| --- | --- |
| `rules` provider: `lossless`, `recoverable`, `stashed` | MSI specs and engines (ADR 0022) |
| `recall` (CLI + MCP), stash, `verify_stashed` | causal necessity labels (ADR 0021) |
| `measure-session`, `share-stats` | `lossy`, Jev and Laya providers, specialist-v3 as a dropper |
| Claude Code plugin (compaction hook), MCP server | semantic retrieval scaffold (ADR 0011/0012) |
| block mode `compact` with cache contract (ADR 0015, `cache-contract-1.0`) | `prepare`/`optimize` cleaning pipeline (works, but not the story) |

Proposal: README and docs index lead with the left column only; the right column moves under
one "Research" heading. ADR 0022 already forbids promoting the MSI oracle arm as product
measurement.

## 2. Where input tokens go (5 real sessions)

### Method

Script: a local scratch script (not committed); PR 1 (item A1) turns it into
`lcc measure-session --input-map`.

- **Billed input** comes from the provider's own usage records in the session file: Claude
  Code `message.usage` per unique `requestId` (uncached, cache write, cache read); Codex
  `token_count.last_token_usage`. These are exact.
- **Category shares** are a replay model: each transcript item (counted with lcc's
  `o200k_base` counter) is charged once per later request, until a compaction boundary. The
  fixed per-request overhead of Claude Code (system prompt, tool schemas, injected
  instructions, none of which are in the JSONL) is the intercept of a least-squares fit of
  billed input on transcript size. Codex rollouts carry the system prompt and tool schemas
  explicitly, so they are counted directly.
- **Approximation.** The fit slope is 1.8–2.6 on Claude Code sessions: billed input grows
  about twice as fast as the transcript as lcc counts it (different tokenizer, re-sent
  thinking: 62k–257k provider thinking tokens per session). The shares below assume one
  ratio across categories. They are good for ranking categories, not for exact percentages.
  On CC-C the fit failed (negative intercept), so its fixed overhead is not reported.
- Attachments count only fields Claude Code renders to the model (hook commands, ids and
  bookkeeping records are excluded).

Sessions (anonymised; all from the maintainer, October 2026):

| id | agent | requests | billed input | cache read share | cache write share of input **cost** (read 0.1×, write 1.25×) |
| --- | --- | ---: | ---: | ---: | ---: |
| CC-A | Claude Code | 945 | 343.3 M | 98.3% | 18.2% |
| CC-B | Claude Code | 782 | 337.0 M | 98.3% | 17.8% |
| CC-C | Claude Code | 204 | 58.7 M | 99.0% | 11.7% |
| CC-D | Claude Code | 774 | 273.0 M | 93.7% | 45.5% |
| CX-A | Codex CLI | 79 | 14.2 M | 97.1% | 23.1% uncached (OpenAI has no write charge; 0.1× read assumed) |

The 0.1/1.25 factors are the ones [CACHE_ALIGNMENT.md](../CACHE_ALIGNMENT.md) uses. All
cache writes in the four CC sessions were 1-hour writes (`ephemeral_1h_input_tokens`), which cost more than 1.25×, so the write share of
cost is a lower bound.

### Share of billed input by category (replay model)

| category | CC-A | CC-B | CC-C | CC-D | CX-A | who controls it |
| --- | ---: | ---: | ---: | ---: | ---: | --- |
| fixed overhead: system prompt, tool schemas, instructions | 8.3% | 10.2% | n/a | 15.3% | 24.8% (prompt 11.8 + schemas 13.0) | harness + user config |
| tool results | 24.7% | 34.3% | 36.6% | 25.9% | 63.2% | tools |
| tool-call inputs (Bash commands, Write/Edit bodies, Agent prompts) | 33.3% | 17.4% | 28.2% | 23.2% | 8.1% | model |
| harness attachments (skill listing, deferred-tool lists, queued notifications, CLAUDE.md, reminders) | 25.5% | 17.4% | 26.0% | 14.3% | 0.4% | harness + user config |
| user text | 5.4% | 17.0% | 8.3% | 15.5% | 0.1% | user |
| assistant text | 2.8% | 3.8% | 0.9% | 5.9% | 3.5% | model |

Drill-down (transcript tokens, counted once):

- **Tool-call inputs** are mostly `Bash` commands (38k–244k tokens per session); 43–79% of
  those command tokens are in commands with a heredoc (`<<`), i.e. scripts or files the agent
  writes inline. Then `Write` bodies (5k–65k).
- **Attachments** are led by the skill listing (13k–49k tokens per session; injected 2–12
  times per session), deferred-tool name lists (8k–18k), CLAUDE.md instructions
  (6k–17k) and the per-turn token reminder (2.5k–11.5k).
- **Re-reads** are small: re-reading a path already read cost 1.3k–11k tokens per session, and
  **identical** re-reads were 0 tokens in all four CC sessions. Duplicate tool outputs of 50+
  tokens: 0–223 tokens. This is why `lossless` and `recoverable` remove ~1%.

### What is cuttable

| category | cuttable today? | could be, keeping the guarantee | how | expected effect |
| --- | --- | --- | --- | --- |
| tool results | **yes**, `stashed` (4.7–36.1% of the lcc view, §1) | larger share if done per payload | stash big outputs **when they arrive**, not at compaction (A2) | hypothesis: cache-safe, per CACHE_ALIGNMENT's placement result |
| tool-call inputs | **no**: EVIDENCE.md says these are never cut | yes: old `Write` bodies and heredoc bodies are model-written and often identical to a file on disk | stash old tool-call inputs with `recall`, or a re-read pointer when the file still matches (A3) | hypothesis: up to the 8–33% share above; the real number is what A1 measures |
| re-reads / duplicates | yes (`lossless`/`recoverable`) | already near the ceiling | none | measured ≤2% of tool results |
| fixed overhead + attachments | **no** (harness-owned) | not by rewriting. lcc can **report** them | config-overhead report: "your skill listing costs N tokens per request" (A4) | user-side decision, nothing rewritten |
| user / assistant text | no, never | no | rule | — |
| cache writes | indirectly | yes: never convert reads into writes | report cost-weighted, not token-weighted; warn when a pass opens an epoch (A5) | 12–46% of input cost was writes in these sessions |

**The main finding.** 94–99% of billed input tokens were cache reads. Cutting a token from a
warm prefix saves 0.1× per later request, but the first request after the cut re-writes
everything to its right at 1.25× or more. So for input cost the order of levers is:
(1) keep big payloads out of the prefix in the first place (per payload), (2) cut at an epoch
the harness opens anyway (compaction: what the plugin does today), (3) never cut mid-prefix on
a warm cache. lcc today does (2) and knows (3); (1) is the missing piece, and it is the
input-side work this plan proposes.

Invariants B1 checks (each over the generator, the corpus and, locally, real sessions):

1. **Idempotence:** `compact(compact(x)) == compact(x)` for `lossless`, `recoverable`,
   `stashed` (block mode keeps its documented relational exception, EDGE_CASES.md).
2. **Verbatim:** every kept span is byte-identical to its source span, in order.
3. **Recall round-trip:** replacing each placeholder with `recall(id)` rebuilds the input
   byte for byte.
4. **No corruption:** CRLF, lone CR, BOM, NFD, zero-width, RTL, surrogate-free text survive
   exactly; output is valid UTF-8.
5. **Stable placeholder:** same removed bytes → same placeholder text and id across runs,
   `PYTHONHASHSEED`, locale and timezone (extends I2/I3 of the cache contract).
6. **Accounting:** report counters reconcile with emitted text.
7. **Fail-closed:** any exception other than the documented `ValueError` / `TranscriptError`
   is a failure.

Tooling choice: the repo deliberately keeps hypothesis out of dev deps (`tests/edge_corpus.py`
header). Decided (§7): add `hypothesis` as a **dev-only** dependency for shrinking (the
failing inputs it finds are much smaller), keep the stdlib generator for the corpus.

## 4. First three PRs

### PR 1: `measure-session --input-map` (A1, with A5's cost split)

- **What:** product version of §2's script inside `src/lcc/session_report.py`: billed
  input from usage records, read/write/uncached split, cost-weighted shares, category replay
  shares with the approximation stated in the output, drill-down (top tools, top attachment
  types, re-reads), Claude Code + Codex. Counts only, offline, JSON + Markdown.
- **Why first:** every other front needs it. A2/A3 need a before/after number, the paper
  needs a per-category table, the Show HN needs a command readers can run on their own
  session, and it is the first input-side feature Lucas asked for. It touches no compaction
  code, so it cannot break the safety core.
- **Done when:** golden tests on synthetic sessions pass; on CC-A it runs in < 10 s and
  matches the scratch script's numbers.

### PR 2: continuous invariant harness (B1 + B2)

- **What:** `tests/invariants.py` with the 7 invariants; a property/fuzz test that runs for
  a time budget (`LCC_FUZZ_SECONDS`, 60 in PR CI, 600 nightly); a versioned
  `tests/corpus/adversarial/` that every run replays; a nightly workflow that logs the seed
  and uploads a minimised failing input as an artifact (no session data, synthetic only).
- **Why second:** A3 and A2 widen what lcc removes. The harness has to exist before the
  removal surface grows, not after.
- **Done when:** the job is green for 7 nightly runs before it gates PRs; a planted bug
  (placeholder id from `hash()`) is caught within the PR budget.

### PR 3: receipt + statusline (C2 + C3)

- **What:** one-line receipt after every pass (CLI and hook), `--receipt` for the full one;
  local ledger written by the hook (counts only); `plugins/claude-code/scripts/statusline.mjs`
  reading it.
- **Why third:** it is the visible part for the beta (weeks 2–3) and the Show HN demo. It
  needs nothing from PR 1 or 2 and can run in parallel with PR 2.
- **Done when:** node tests on a fixture ledger; a screenshot of a real session's statusline

### 6.1 Paper 1 skeleton

**Working title:** Recoverable verbatim compaction for coding-agent context: a pre-registered
study of stash-and-recall

1. **Introduction.** Agents re-send their whole history; summaries drop exact values.
   Question: can old tool outputs leave the context without loss, if the agent can fetch them
   back byte for byte?
2. **Related work.** Prompt compression, summarisation-based compaction (Claude Code
   `/compact`), memory paging and retrieval for agents, prompt caching. (To be surveyed.)
3. **Method.** The `rules` modes; the stash (content-addressed, hash-checked); `recall`; the
   cache contract (I1–I4) and why placement matters for cache cost.
4. **Mechanical study** (`stashed-v1`): 847 sessions, 45.6 M tokens, reduction per mode,
   10,830 stashed results with 0 violations by two independent checkers (EVIDENCE.md §1).
5. **Agent-in-the-loop study** (`stashed-recall-v1`, pre-registered): 172 requests, three
   arms, the two pre-registered tests, recall behaviour (EVIDENCE.md §2).
6. **Verbatim vs summary** (`probe-eval-v1`) and the matched-budget arms (new, gap 3).
7. **Cost**, including recall turns (new, gap 2) and the input map of where tokens go (§2 of
   this plan, extended to more sessions).
8. **External replication**: sessions from other users (gap 1).
9. **Limitations**: one maintainer's sessions for the main studies, one answerer (until gap
   4), LLM judges, questions built to need removed content (19 of 662 natural).
10. **Artifact**: MIT code, commands to reproduce every mechanical number, protocol and
    amendments.

### 6.2 Show HN draft

> **Show HN: lcc – compact coding-agent context without summarizing it away**
>
> Claude Code's /compact replaces your session with a model-written summary. In my sessions
> that summary lost exact details: on 172 real requests, a summary of the same context got
> 73% of exact values right, against 98% for the full context. (The summary was our own
> reimplementation of /compact, written by Opus, not Claude Code itself.)
>
> lcc does something narrower. It moves old tool outputs (file reads, command output) out of
> the context into a local stash and leaves a one-line pointer. The agent can call `recall`
> to get any of them back byte for byte. User and assistant messages are never touched. It
> runs offline, with no model and no network.
>
> On those 172 requests, an agent with the stashed context plus `recall` matched full context
> on file recall (+0.006, 95% CI −0.023 to +0.034) using 36.6% fewer context tokens. It
> called `recall` for 90% of the questions about removed content. The test was
> pre-registered.
>
> The limits: all of this is my own sessions (847 for the mechanical numbers, 266 long ones
> for the 22.7% median cut), one answerer model, one run. That is why the first thing in the
> README is a command you can run on your own session:
>
>     uvx local-context-compiler measure-session ~/.claude/projects/<project>/<session>.jsonl
>
> It counts only and sends nothing. If you post the output, I'll add it to the evidence page,
> separately from mine.
>
> Code (MIT): github.com/lucasmartins-ai/lcc · Evidence and method: docs/EVIDENCE.md

(The `uvx` line assumes F2 lands; the current README uses `pip install`.)
